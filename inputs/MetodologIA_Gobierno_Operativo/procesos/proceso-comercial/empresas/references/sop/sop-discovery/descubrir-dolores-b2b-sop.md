# SOP: Descubrir Dolores B2B

**Versión:** 2.0
**Fecha:** 2026-03-24
**Dueño:** Sales Executive / Solution Architect
**Duración:** 20-40 días
**Objetivo:** Validar dolores, mapear impacto comercial, construir business case con datos del cliente

---

## 1. Propósito

Proceso de DISCOVERY: profundización sistemática en entendimiento de problemas del cliente, cuantificación de impacto comercial, y validación de solución conceptual.

**Incluye:**
- Preparar y ejecutar calls de discovery estructurado (3-5 calls con diferentes stakeholders)
- Mapear proceso actual y brechas (análisis GAP)
- Cuantificar impacto comercial (% costo reducido, días ahorrados, ingresos incrementales)
- Validar solución conceptual (cliente confirma que enfoque es viable)
- Alinear stakeholders múltiples (CxO, usuarios, IT, financial)
- Construir business case (ROI, payback, business justification)
- Calificar y gatekeep en Gate D1

---

## 2. Supuestos Explícitos del SOP

| # | Supuesto | Validación |
|---|----------|-----------|
| S1 | Cliente tiene 3+ stakeholders accesibles (CxO, usuarios, IT/finance) | Confirmar en primer call de discovery |
| S2 | Cliente tiene datos internos (procesos, costos, timelines) disponibles para análisis | Solicitar documentos o data en segundo call |
| S3 | Solution Architect disponible para 2-3 calls de discovery (validación técnica) | Coordinar con SA Manager semana 2 de discovery |
| S4 | Cliente dispuesto a hacer time investment (3-5 calls, 3-5 horas total) | Si cliente no disponible, riesgo alto, descalificar |
| S5 | Pain identificado en Scouting es sintomático de problema más profundo (no superficial) | Validar en Discovery. Si es superficial, descalificar |

## 4. Fase 1: Preparación de Discovery

### Paso 1.1: Diseñar plan de discovery calls (Día 1-2)
**Actividad:** Definir 3-5 calls con stakeholders diferentes.

**Estructura recomendada:**
1. **Call 1 (Sponsor CxO):** Business pain, impact, presupuesto, decision timeline
2. **Call 2 (Usuarios operacionales):** Problemas día-a-día, workarounds, impacto
3. **Call 3 (IT/Technical):** Arquitectura actual, constraints técnicos, integraciones
4. **Call 4 (Financial/CFO):** Budget, capex vs opex, ROI expectations
5. **Call 5 (Optional: Other stakeholder):** Si existe otro departamento afectado

**Checklist:**
- ¿Tenemos 3+ stakeholders identificados? → SÍ / NO
- ¿Hemos agendar 3+ calls (no todas el mismo día)? → SÍ / NO
- ¿Cada call tiene objetivo específico definido? → SÍ / NO

**Output:** Calendario de discovery calls (próximos 2-3 semanas).

### Paso 1.2: Preparar guiones de discovery por stakeholder
**Para cada stakeholder, definir 5-7 preguntas clave:**

**Sponsor CxO:**
- Cómo describes el problema actual?
- Cuál es el impacto en números (costo, tiempo, ingresos)?
- Quién else debe estar involucrado en decisión?
- Cuándo necesitas resolver esto?
- Cuál es el presupuesto típico para iniciativas como esta?

**Usuarios operacionales:**
- Cuáles son los 3 mayores problemas que enfrentas en tu día-a-día?
- Cómo impacta esto tu trabajo (tiempo, calidad, frustración)?
- Cuál sería ideal state para ti?
- Cuáles son las barreras para cambiar el proceso actual?
- Quién más está afectado por este problema?

**IT/Technical:**
- Cuál es tu arquitectura actual (sistemas, integraciones, cloud vs on-prem)?
- Cuáles son los constraints técnicos (legacy systems, compliance, security)?
- Qué hace difficile resolver este problema internamente?
- Qué necesitarías de una solución externa (integraciones, APIs, data format)?
- Cuál es tu rol en la decisión?

**Financial/CFO:**
- Cuál es el impacto financiero del problema (costo actual, oportunidad cost)?
- Cómo se presupuesta iniciativas como esta (capex vs opex)?
- Cuál sería el ROI aceptable para ustedes?
- Cuál es el timing para presupuesto?
- Quién aprueba inversión final?

## 5. Fase 2: Ejecutar Discovery Calls

### Paso 2.1: Guion general para todos los calls (30-45 min)
**Estructura de cada call:**

1. **Apertura (3 min):**
   - Confirmar tiempo disponible
   - Resumen rápido: "We want to understand [problem context] deeper so we can explore if there's a good fit."

2. **Discovery Questions (25-30 min):**
   - Preguntas específicas para stakeholder
   - Técnica: Ask, listen, probe deeper
   - Buscar: números, impacto, urgencia
   - NO interrumpir, NO hacer pitch

3. **Solution Conceptual Validation (10 min):**
   - Describe approach general: "Based on what I'm hearing, an approach would be [high-level solution concept]. Does that resonate?"
   - Escuchar feedback
   - Ask: "What would need to be true for this approach to work for you?"

4. **Close (2-3 min):**
   - Resumen: "So it sounds like [problem] impacting [stakeholder] with cost of [X]. If we could solve this in [timeline], would that be valuable?"
   - Next step: "I'd like to come back with [other stakeholder] to validate this with them."

### Paso 2.2: Tomar notas y documentar aprendizajes (Post-call, 15 min)
**Campos a registrar en CRM:**

| Field | Valor |
|-------|-------|
| Stakeholder Name | [Nombre] |
| Call Date | [Fecha] |
| Problems articulated | [Lista de problemas mencionados] |
| Impact (financial or operational) | [Números si disponibles] |
| Current process description | [Cómo funciona hoy] |
| Ideal state (per stakeholder) | [Lo que quieren lograr] |
| Technical constraints | [Si aplica - barriers to solution] |
| Stakeholder's role in decision | [Sponsor, influencer, blocker, etc.] |
| Alignment with other stakeholders | [Mencionar si hay alineación con otros o desalineación] |
| Next steps | [Recomendación de quién más entrevistar] |

### Paso 2.3: Asegurar Solución Arquitectura en Call 3 (con IT) (Día 10-15)
**Actividad:** Solicitar participación de Solution Architect en Call 3 (IT/Technical).

**SA participación:**
- Escuchar constraints técnicos
- Validar feasibility de solución conceptual
- Identificar integraciones requeridas
- Confirmar que solución es viable técnicamente
- Tomar notas sobre architecture direction

**Post-call SA:**
- Email a Sales: "Solución conceptual es técnicamente viable. Recomendaciones: [...]"
- Nota en CRM: "SA validation - PASS" o "REQUIRES ALTERNATE APPROACH"

## 6. Fase 3: Análisis y Cuantificación

### Paso 3.1: Construir análisis de brecha (GAP) (Día 15-20)
**Actividad:** Documento que compara estado actual vs estado deseado.

**Estructura de GAP analysis:**

```
CURRENT STATE (HOY)
- Proceso: [Descripción de cómo funciona ahora]
- Herramientas utilizadas: [Sistemas, apps, spreadsheets]
- Problemas: [Lista de problemas identificados]
- Impacto: [Costo, tiempo, calidad, riesgo]

DESIRED STATE (MAÑANA, CON SOLUCIÓN)
- Proceso: [Cómo funcionaría idealmente]
- Herramientas utilizadas: [Sistemas, apps que serían necesarios]
- Beneficios esperados: [Problemas resueltos]
- Impacto: [Costo reducido, tiempo ahorrado, calidad mejorada]

BRECHA (GAP)
- Qué falta hoy para lograr desired state
- Quién puede resolverlo (interno vs externo)
- Tiempo estimado para resolver
- Costo de NO resolverlo (business case)
```

**Checklist:**
- ¿Hemos documentado state actual con datos del cliente? → SÍ / NO
- ¿Hemos documentado desired state con input de stakeholders? → SÍ / NO
- ¿Brecha está cuantificada (no es vaga)? → SÍ / NO

### Paso 3.2: Cuantificar ROI (Día 20-25)
**Actividad:** Calcular retorno de inversión en números que cliente entiende.

**Métricas de impacto a cuantificar:**

**Opción A: Costo Reducido**
- Costo actual (salarios, herramientas, error correction): $X/año
- Costo con solución: $Y/año
- Ahorro anual: $X - $Y = $Z/año
- Payback (si cuesta implementar $K): K / Z = M meses

**Opción B: Tiempo Ahorrado**
- Horas gastadas actualmente en [proceso]: N horas/semana
- Horas gastadas con solución: M horas/semana
- Horas ahorradas: N - M = P horas/semana
- Valor del tiempo ahorrado: P * $[costo hora] = $Q/año
- Payback: K / Q = M meses

**Opción C: Ingresos Incrementales**
- Oportunidad perdida actual (debido a problema): $R/año
- Oportunidad capturada con solución: $S/año
- Incremento de ingresos: $S - $R = $T/año
- Payback: K / T = M meses

**Ejemplo de ROI:**
> "Hoy gastan 20 horas/semana en [proceso manual]. Con solución, serían 2 horas. Ahorro: 18 horas/semana * $50/hora * 50 semanas/año = $45,000/año. Si solución cuesta $100,000 implementar, payback es 2.2 años. Y en años 2-3, es puro ahorro de $45,000/año."

**Checklist:**
- ¿Hemos cuantificado impacto en números (no vago)? → SÍ / NO
- ¿Numbers son basados en data del cliente (no nuestras assumptions)? → SÍ / NO
- ¿Payback period es razonable (<2-3 años típicamente)? → SÍ / NO
- ¿Cliente confirm que números son "ballpark correct"? → SÍ / NO

### Paso 3.3: Construir Business Case (Día 25-30)
**Actividad:** Documento de 1-2 páginas que resume pain, impact, and recommendation.

**Estructura de Business Case:**

```
EXECUTIVE SUMMARY
- Problema identificado: [Pain statement en 1 frase]
- Impacto: [ROI en números]
- Recomendación: [Proceder con solución conceptual X o Y]

CURRENT STATE & PAIN
- Proceso actual: [Brief description]
- Problemas: [Top 3 problems]
- Impact on business: [Cost, time, revenue impact]

PROPOSED SOLUTION (HIGH LEVEL)
- Approach general: [Cómo lo resolveríamos]
- Timeline estimate: [Weeks/months]
- Investment required: [Budget range]

ROI / BUSINESS JUSTIFICATION
- Cost of solution: $X
- Annual benefit: $Y
- Payback period: Z months
- Year 2-3 benefit: $Y/year (no additional cost)

STAKEHOLDER ALIGNMENT
- Sponsor (CxO): ALIGNED
- Users (operations): ALIGNED
- IT/Technical: ALIGNED or CONSTRAINTS (list)
- Finance/CFO: ALIGNED or QUESTIONS (list)

NEXT STEPS
- Confirm this Business Case with [list stakeholders]
- Proceed to detailed proposal and architecture design
- Target decision date: [Date]
```

**Checklist:**
- ¿BC resume claramente pain y ROI? → SÍ / NO
- ¿Números son basados en data cliente? → SÍ / NO
- ¿Stakeholder alignment está documentada? → SÍ / NO
- ¿Cliente ha confirm BC es accurate? → SÍ / NO

## 7. Fase 4: Cierre de Discovery y Gate D1

### Paso 4.1: Validación Final Stakeholders (Día 30-35)
**Actividad:** Confirmar con TODOS stakeholders que:
1. Pain identificado es correcto
2. Solution conceptual es viable
3. ROI es aceptable
4. Timeline es realista

**Método:**
- Email Business Case a todos stakeholders: "Here's our summary of discoveries and proposed approach."
- Llamada grupal (30 min) con CxO + usuario + IT + finance: "Walk through BC, gather feedback, confirm alignment."
- Si desalineación existe, rewind a discovery (ej: IT tiene constraint técnico que requiere revisión solución).

### Paso 4.2: Aplicar Gate D1 (Día 35-40)
**Criterios binarios de calificación:**

- ¿Análisis de brecha (GAP) completado con datos cliente? → **SÍ / NO**
- ¿ROI cuantificado (% ahorro, días ahorrados, ingresos incrementales)? → **SÍ / NO**
- ¿3+ stakeholders entrevistados, alineados con sponsor? → **SÍ / NO**
- ¿Solución conceptual validada por cliente (no rechazo técnico)? → **SÍ / NO**
- ¿Presupuesto confirmado o aprobación en proceso documentada? → **SÍ / NO**

**Decisión:**
- **SI en 5/5:** PASAR a Structuring (prioridad: HIGH)
- **SI en 4/5:** PASAR a Structuring (prioridad: MEDIUM)
- **SI en 3/5 o menos:** DESCALIFICAR o HOLD

**Output:** Oportunidad en CRM estatus "Discovery - Qualified" o "Discovery - Descalified"

## 8. Casos Borde de Discovery

### Caso Borde 1: IT/Technical no puede asistir a call
**Escenario:** IT Manager no está disponible en semana 2-3.

**Acción:** Agendar IT call en semana 4. Mientras tanto, hacer discovery con usuarios y sponsor.

**Fallback:** Si IT no participa nunca, riesgo alto (pueden bloquear en Structuring). No avanzar sin IT input.

### Caso Borde 2: Stakeholders desalineados (IT vs Business)
**Escenario:** CxO quiere cloud, IT Manager dice "Debe ser on-prem por compliance."

**Acción:**
1. Escalada inmediata: Reunión 1:1 con IT + CxO
2. Entender constraint: "¿Es hard requirement o hay flexibility?"
3. Si hard requirement, solución conceptual debe cambiar (on-prem)
4. Si hay flexibility, documentar "bajo ciertas condiciones (ej: data masking), cloud es viable"

**Fallback:** Si desalineación es irreconciliable, descalificar.

### Caso Borde 3: Cliente no tiene data para cuantificar ROI
**Escenario:** "No sabemos exactamente cuánto cuesta ese problema hoy."

**Acción:**
1. Solicitar: "¿Tienes aproximación? Ej: ¿20 horas/semana? ¿$2M/año?"
2. Si cliente no tiene ni approximación, preguntar: "¿Cuáles serían los impactos cuantitativos si se resuelve?"
3. Usar "guesstimate" basado en industry benchmarks (comunicar asunción claramente)

**Fallback:** Si NO hay forma de cuantificar, ROI no es claro, descalificar.

### Caso Borde 4: Sponsor dice "Presupuesto existe pero no puedo decir exactamente cuánto"
**Escenario:** CxO confirma hay presupuesto pero es confidencial internamente.

**Acción:** Aceptar confirmación verbal. Documentar en CRM: "Sponsor confirmed budget exists for this priority."

**Fallback:** No es problema. Presupuesto confirmado, aun si no sabe monto exacto.

### Caso Borde 5: Discovery se estira >40 días (cliente lento)
**Escenario:** Cliente tarda en responder, cancela calls, pide postergación.

**Acción:**
1. Diagnóstico (Día 30): ¿Problema es cliente o es nuestro?
2. Llamada 1:1 con sponsor: "¿Siguen siendo prioridad o ha cambiado?"
3. Opciones: fijar dates (próximos 3 calls en próximas 2 semanas), o pausa formal (reactivación en Q2)
4. Máximo: 60 días totales (Scouting + Discovery)

**Fallback:** Si no hay urgencia, descalificar.

## 9. Anti-Patterns de Discovery

### AP1: "Discovery infinita sin estructurar"
**Anti-pattern:** 8+ calls sin nunca "validar y pasar a Structuring."

**Qué hacer:** Discovery máximo 4-5 semanas. Gate D1 en Day 40.

### AP2: "Descubrir sin cuantificar"
**Anti-pattern:** Entender pain pero no calcular ROI.

**Qué hacer:** SIEMPRE cuantificar. Si cliente no tiene data, usar approximations (documentar).

### AP3: "Solo hablar con sponsor"
**Anti-pattern:** Solo 1 call con CxO, no entrevistar usuarios ni IT.

**Qué hacer:** Mínimo 3 calls con stakeholders diferentes.

### AP4: "Propuesta en Discovery"
**Anti-pattern:** En Discovery call, mandar propuesta o arquitectura detallada.

**Qué hacer:** Discovery es exploración. Structuring es propuesta. Separar.

### AP5: "Ignoring technical constraints"
**Anti-pattern:** IT dice "Esto no funciona con nuestros sistemas" pero Sales ignora.

**Qué hacer:** Tomar seriamente constraints técnicos. Escalar a SA para validar feasibility alternativa.

## 10. Decisiones de Diseño del SOP

### DD1: ¿Por qué 3-5 calls separados, no 1 call grupal?
**Justificación:** Cada stakeholder tiene perspectiva diferente. Calls 1:1 generan more candid feedback. Calls grupo = "groupthink."
**Validación:** 1:1 discovery = 95% articulation de pain. Grupo = 60% (alguien siempre calla).

### DD2: ¿Por qué SA participa en Discovery, no en Scouting?
**Justificación:** Discovery requiere validación técnica (feasibility). Scouting no. SA es recurso escaso, solo entra cuando pain + ROI validados.
**Validación:** SA en Discovery + Structuring = 85% propuestas técnicamente OK. SA no en Discovery = 40% propuestas rechazadas en Structuring.

### DD3: ¿Por qué requerimos presupuesto confirmado en Gate D1?
**Justificación:** Si presupuesto no existe en Discovery, riesgo de structuring solución "de fantasía." Mejor validar temprano.
**Validación:** Presupuesto confirmado en Discovery = 80% de deals en Structuring cierran. Sin presupuesto = 30% cierran.

## 11. Fallbacks Operativos

### FB1: Cliente no responde para agendar calls
**Plan A:** Email 1: Proponer 3 opciones de timing.
**Plan B:** Email 2 (Day 5): "We want to move forward, need 3-5 calls over next 2 weeks. What's your availability?"
**Plan C:** Email 3 (Day 10): Preguntar si timing es incorrecto o si priorlda cambió.
**Fallback:** Si no hay respuesta Day 15, asumir no es prioridad. Downgrade a "Hold" o descalificar.

### FB2: Solución conceptual es rechazada por IT
**Plan A:** SA meets con IT, entender objeción específica.
**Plan B:** SA propone 2-3 opciones técnicas alternativas.
**Plan C:** Nueva llamada con IT para validar alternativa.
**Fallback:** Si IT rechaza todas alternativas, descalificar.

### FB3: ROI es borderline (payback >3 años)
**Plan A:** Preguntar: "¿Sería aceptable payback de X años?" Si no, problem.
**Plan B:** Explorar "hidden benefits" no cuantificados (risk reduction, employee satisfaction, etc).
**Plan C:** Si ROI no mejora, descalificar.
**Fallback:** ROI debe ser <3 años típicamente, o deal es "nice-to-have" no "must-have."

### FB4: Stakeholders desalineados en Gate D1
**Plan A:** Escalada 1:1 con CxO + stakeholder desalineado.
**Plan B:** Entender constraint o objeción.
**Plan C:** Rewind a Discovery si requiere validación adicional.
**Fallback:** Si desalineación es irreconciliable, descalificar.

## 12. Métricas de Discovery

| Métrica | Target | Acción |
|---------|--------|--------|
| Calls completed | 4-5 | Si <3, no avanzar a Structuring |
| Stakeholders entrevistados | 3+ | Si <3, incomplete discovery |
| GAP analysis completado | 100% | Si no, no gate-keepers |
| ROI cuantificado | 100% | Si no quantified, descalificar |
| Discovery duration | 20-35 días | Si >40 días, downgrade |
| Gate D1 qualification | 40-60% | Si <30%, discovery muy strict. Si >70%, maybe too lenient |
